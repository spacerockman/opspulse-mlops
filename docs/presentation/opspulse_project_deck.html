01 · 客户现状与痛点（为什么需要这个项目）

客户要解决什么问题？（现有 v0.1 系统的三大痛点）

痛点 1：狼来了误报疲劳

72% 误报

促销/业务高峰期 CPU 涨到 87%，但延迟和错误率完全健康。现行 CPU > 85% 静态阈值疯狂告警（v0.1 实测整体误报率 36%）。

痛点 2：缓慢故障漏报

0% 召回

缓慢内存泄漏在 OOMKill 崩溃前 CPU 与 5xx 尚未超标，v0.1 静态规则实测早期召回率为 0/200 (0%)，只能等服务宕机后被动救火。

痛点 3：模型失控 & MTTR 长

人工救火

团队不敢上线 ML 模型（无门禁、无漂移监控、无回滚手段）；告警响后 SRE 需手动翻查日志和日语 Runbook，恢复耗时极长。

客户核心诉求一句话总结

「我要一套比规则更准（少误报、不漏报）、上线有门禁、出事 3 分钟内能回滚、分布变了能提醒我审批再重训，并且告警时自动把日语排查手顺书和命令递给值班人员的轻量省钱平台。」

核心工程原则 #1：Local-Cloud Parity

本地用 MinIO 模拟 S3、Docker 模拟 ECS，仅通过环境变量切换，避免“本地好好的上云全崩”。

05 · 技术选型与取舍理由（日本面试高频考点）

为什么选这套技术栈？（而非盲目堆大厂全家桶）

模块 选定技术 不选替代方案的理由（Engineering Trade-off）
模型 LightGBM + IsolationForest 不选 PyTorch/LSTM：表格时序指标 10ms 内 CPU 可训可推，且可解释性强（Top-3 贡献特征）。
模型注册 MLflow Aliases (@champion) 不用已废弃的 Stages API，紧跟 MLflow 2.x+ 最新标准。
云平台 AWS ECS Fargate + Terraform 不选 EKS/Kubeflow/SageMaker：小团队上 K8s 运维与控制面成本（$73+/月）喧宾夺主。
网络控费 公有子网 + 严格 SG（无 NAT） 省去 NAT Gateway 固定月租（约 $32/月），将 AWS 演练费用压到一杯咖啡钱。
LLMOps Langfuse Cloud (免费层) 不在本地 Docker 自建 Langfuse v3（需 ClickHouse+Redis 极重），零运维专注评估本身。
数据替代 自建 SaaS 模拟器 + AI4I 扩展 不用静态 Loghub 孤立日志，确保指标/日志/漂移/线上推理端到端全链路打通。
